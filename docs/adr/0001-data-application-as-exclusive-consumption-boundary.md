# 以数据应用作为专属外部消费场景边界

数据服务平台使用“数据应用”替代“消费应用”，每个数据应用只对应一个外部消费场景和一套独立调用身份，不允许多个场景共享数据应用或凭据；这样选择是为了避免多对多关系导致凭据轮换、撤销、配额、审计和运行故障相互影响。

API、Agent、MCP、模型、Skill、Worker 等产品仍可在租户内共有复用，但每个数据应用必须固定能力版本，并分别维护权限、凭据、配额和运行观测；开发修改只有经过申请、分项审批和整体发版后才能替代当前运行版本。数据应用创建或更新审核通过后，所需网关策略由系统依据批准结果自动绑定和分配，并作为同一次发版执行的一部分；策略分配失败或冲突时，新版本不得部分生效，旧运行版本继续提供服务。

数据应用首次保存草稿时生成稳定且非秘密的 App ID，该标识不得重新生成；需要新 App ID 等同于创建新的数据应用。API Key、Client Secret 等秘密凭据与 App ID 分离，只有应用版本和全部必需授权项批准、策略准备下发后才签发，完整值只展示一次。保持认证配置不变的凭据轮换不创建应用版本，但必须二次确认、立即使旧凭据失效并保留审计；认证方式、有效期策略或授权范围变化仍进入新的应用版本。

应用选择服务时递归固定其传递依赖闭包，直至最终数据表、字段、行范围和操作权限。审批同时保留服务到权限的每条来源路径，并对共享依赖去重形成授权清单；任一必需依赖未获批准时，整个应用版本不得部分生效。

这一边界以增加数据应用数量、提高整体发版执行约束为代价，换取调用身份、策略归属和运行影响的明确隔离。
