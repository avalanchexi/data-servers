# API 服务三种开发方式调研

> 调研日期：2026-08-26  
> 适用范围：数据中台“数据服务”模块中的 API 服务  
> 资料边界：只使用官方产品文档、官方规范和政府标准；没有找到与本项目完全对应的“数据服务 Coding Agent”官方产品，因此相关方案明确标记为本项目设计推断

## 1. 结论摘要

### 1.1 核心结论

1. **传统开发、低代码开发、Coding Agent 辅助开发应被建模为三种创作入口，而不是三种 API 服务产品。** 三种入口最终都必须形成同一种 `APIServiceDraft`、OpenAPI 契约、测试证据、服务版本和上线申请；服务集市、授权、统一网关和运行管理不应感知开发入口差异。
2. **传统开发**以 SQL／Dynamic SQL 为主要实现表达，适用于同源多逻辑表、复杂条件和高级查询；开发者直接控制实现，并承担 SQL、参数契约和返回契约的一致性责任。
3. **低代码开发**以受约束的查询模型为实现表达，首期建议严格限制为单张 ADS 逻辑表；开发者选择请求条件、操作符、返回字段、排序和分页，平台生成查询语句和接口契约。
4. **Coding Agent 不是新的运行时实现类型。** 它是对传统或低代码草稿提出补丁的协作入口：根据自然语言需求生成或修改来源选择、SQL、参数契约、OpenAPI 片段和测试用例，但不得绕过已有权限，不得直接提交上线，不得审批或发布。
5. 三种入口必须复用：服务标识和元数据、ADS 来源绑定、开发权限、请求／返回契约、运行配置、测试用例与测试结果、版本、上线／下线、审批、环境部署、服务集市可见性和运维数据。
6. 三种入口必须保持差异：主体编辑器、入口级校验、转换规则，以及 Coding Agent 的生成依据、变更差异、采纳确认和生成溯源。不能为了界面统一而把 SQL 编辑器、字段勾选器和 Agent 对话合成同一种编辑体验。
7. **上线版本必须不可直接修改。** 修改线上 API 时创建新草稿版本；测试环境可以直接部署，生产上线必须经过开发者提交和管理者审核。测试环境发布和生产上线是环境行为，不是开发方式专属流程。
8. Dynamic SQL 中消费者输入应优先使用类型感知的参数绑定。火山引擎明确提醒 `#{}` 可降低 SQL 注入风险，而 `${}` 是直接插入；本项目应把 `${}` 限制为经过白名单验证的标识符等特殊场景。

### 1.2 最重要的领域建模修正

界面可以展示三个入口卡片：

```text
传统开发｜低代码开发｜Coding Agent
```

但内部不应使用一个三值字段同时表达“实现是什么”和“由谁编辑”。推荐拆成两个维度：

| 维度 | 示例值 | 含义 |
|---|---|---|
| 实现表达 `implementationRepresentation` | `SQL_TEMPLATE`、`LOW_CODE_QUERY_MODEL` | 当前草稿用什么可执行表达保存 |
| 创作来源 `authoringOrigin` | `MANUAL_SQL`、`LOW_CODE`、`AGENT_ASSISTED` | 当前修订最初或最近通过何种入口产生 |

原因是 Coding Agent 最终仍需生成 SQL 模板或低代码查询模型；它本身不应成为网关能够执行的第三种 API 制品。

## 2. 研究方法与证据边界

本研究以火山引擎 DataLeap 数据服务作为传统／低代码流程的主要一手样本，并用 OpenAPI 官方规范确定统一接口契约的边界。Coding Agent 方面没有找到“在数据中台内通过 Agent 生成数据 API 并走同一上线流程”的完全对应官方产品，因此只采用以下一手材料提炼安全模式：

- GitHub 官方 Coding Agent 文档：Agent 在受限分支产生变更，不能自行批准或合并，必须由人审查；
- NIST DevSecOps 官方材料：AI 生成内容必须由人监控和验证，AI 辅助修改需要可追踪并接受不低于人工修改的审查；
- OpenAPI 官方规范：用统一、机器可读的 HTTP API 描述承载路径、参数、响应和安全方案。

报告中的表述分为三类：

- **官方事实**：来源明确声明的产品能力或规范要求；
- **项目已定**：本项目 `CONTEXT.md` 已确认的约束；
- **设计建议**：由官方事实和本项目约束推导出的方案，不代表被参考产品已经实现。

## 3. DataLeap 官方流程基线

### 3.1 创建类型并不等于本项目三种入口

**官方事实**：DataLeap 的 API 开发提供脚本式、向导式和原生式三种类型：

- 脚本式允许开发者自行编写查询 SQL，支持同源多张逻辑表；
- 向导式通过勾选界面配置生成 SQL，请求参数映射为 `WHERE` 条件，返回参数映射为 `SELECT` 字段，只支持单张逻辑表；
- 原生式允许调用方在已圈选逻辑表范围内动态传入 SQL，面向动态分析场景。

DataLeap 还要求开发者加入数据服务项目，并具备相应角色、逻辑表读权限；创建时配置 API 名称、目录、最大 QPS、安全等级、最大 limit、告警、初始版本和版本描述。[火山引擎 DataLeap：API 开发](https://docs.volcengine.com/docs/6260/127699?lang=zh)

**设计结论**：DataLeap 的“原生式”不是 Coding Agent，不能拿它证明 Coding Agent 能力。本项目首期的三种入口应对应：

| 本项目入口 | DataLeap 可验证参考 | 关系 |
|---|---|---|
| 传统开发 | 脚本式 | 直接参考 SQL、Dynamic SQL、参数解析和测试交互 |
| 低代码开发 | 向导式 | 直接参考单表、条件和返回字段勾选交互 |
| Coding Agent | 无完全对应类型 | 本项目新增的辅助创作入口，必须单独定义人审和权限边界 |

DataLeap 的原生式会把动态 SQL 查询能力交给调用方，安全模型和普通固定契约 API 不同，不建议纳入本项目首期 API 开发三入口。

### 3.2 DataLeap 的公共开发和生命周期事实

根据 DataLeap 官方 API 开发文档，三种 DataLeap API 类型共享以下流程：[火山引擎 DataLeap：API 开发](https://docs.volcengine.com/docs/6260/127699?lang=zh)

1. 创建文件夹并新建 API；
2. 选择创建类型，填写基本信息和更多配置；
3. 保存后进入相应开发页面；
4. 保存当前版本、另存为新版本或另存为新 API；线上版本不允许直接保存修改；
5. 在开发页面测试，查看结果、日志、请求体、状态和耗时；
6. 发布到测试环境或线上环境；测试环境无需审核，线上环境按项目配置触发审核；
7. 在版本列表查看发布环境、执行发布／下线／删除未发布版本／版本对比；
8. 已发布 API 进入授权、限流、报警和调用监控。

**设计结论**：创建入口可以不同，但版本、测试、发布环境、审批、授权和运维天然适合共享。这与本项目“同一草稿和生命周期”的既有决定一致。

## 4. 传统开发

### 4.1 输入

**官方事实**：DataLeap 脚本式开发允许选择同源多张逻辑表，文档当前写明最多 10 张；开发者编写普通 SQL 或 Dynamic SQL，并配置请求参数、返回参数、返回格式和缓存策略。[火山引擎 DataLeap：API 开发—脚本式](https://docs.volcengine.com/docs/6260/127699?lang=zh#_4-1-%E8%84%9A%E6%9C%AC%E5%BC%8F)

**项目已定／设计建议**：本项目传统开发输入应包含：

- 服务名称、负责人、描述、服务类型、目录／业务分类；
- 一个或多个已获开发权限的 ADS 逻辑表；
- 普通 SQL 或 Dynamic SQL 模板；
- 请求参数的名称、类型、必填、操作符、默认值、样例、说明和字段映射；
- 返回字段的名称、类型、必返、排序、样例、说明和字段映射；
- 分页、最大返回行数、查询超时、缓存、最大 QPS 等运行约束；
- REST 方法、路径和 OpenAPI 契约元数据；
- 至少一个可重复执行的测试用例。

本项目已规定 API 只能引用 ADS 层资产；DataLeap 的“同源”限制可以作为首期多表开发的技术参考，但是否成为本项目硬限制仍应由底层查询引擎和总体架构决定。

### 4.2 编辑体验

**官方事实**：DataLeap 脚本式编辑器提供运行、解析请求参数、查看表字段、格式化、全屏等能力。运行可以解析请求／返回参数，并展示查询结果和日志；请求参数也可以手工补充和校正。[火山引擎 DataLeap：API 开发—脚本式](https://docs.volcengine.com/docs/6260/127699?lang=zh#_4-1-%E8%84%9A%E6%9C%AC%E5%BC%8F)

**官方事实**：DataLeap Dynamic SQL 使用 XML 风格模板，支持 `if`、`choose`、`where`、`foreach`、`bind` 和 `function` 等元素。`#{}` 根据参数类型生成 SQL 片段，`${}` 直接插入数据；官方明确建议尽量使用 `#{}` 以降低 SQL 注入风险。[火山引擎 DataLeap：Dynamic SQL 语法](https://docs.volcengine.com/docs/6260/1254733?lang=zh)、[火山引擎 DataLeap：OneService 语法](https://docs.volcengine.com/docs/6260/127701?lang=zh)

**设计建议**：传统开发页面必须保留代码优先交互，至少包括：

- 左侧 ADS 逻辑表和字段浏览器；
- 中间 SQL／Dynamic SQL 编辑器；
- 参数解析、SQL 格式化、静态校验、Dry Run 和执行测试；
- 右侧请求／返回契约与 OpenAPI 预览；
- SQL 变更与契约变更的同步提示，不能静默覆盖开发者手工调整的参数。

### 4.3 校验

**设计建议**：提交测试前执行分层校验：

1. **来源校验**：全部来源属于当前租户、ADS 层、当前业务域允许范围，且开发者拥有开发数据权限；
2. **SQL 校验**：只允许平台支持的只读查询语法，拒绝 DDL、DML、多语句和未授权对象；
3. **Dynamic SQL 校验**：XML／模板结构完整；消费者可控值默认必须使用类型化绑定；`${}` 只允许绑定经白名单验证的表名、字段名等标识符；
4. **契约校验**：SQL 占位符与请求参数一一对应；返回表达式与返回 Schema 一致；字段类型、必填、默认值和操作符合法；
5. **数据安全校验**：请求和返回字段不能超过获批的数据范围；敏感字段必须满足脱敏、行列权限和安全等级规则；
6. **资源校验**：最大 limit、超时、QPS 和缓存符合租户及服务策略；
7. **OpenAPI 校验**：路径、方法、参数、响应和安全方案能够生成有效的 OpenAPI 文档。

其中第 1、5、6 项属于本项目治理要求；DataLeap 官方材料主要证明了逻辑表权限、参数解析、安全等级、最大 limit、QPS 和测试能力，并不能证明上述全部策略已在 DataLeap 中按同样方式实现。

### 4.4 测试、版本和上线

传统开发使用第 7 节定义的统一流程，不应拥有单独生命周期。SQL 专属测试证据应额外保存：解析后的最终 SQL、执行计划或成本信息（底层引擎支持时）、请求参数快照、查询日志和结果 Schema。

## 5. 低代码开发

### 5.1 输入

**官方事实**：DataLeap 向导式开发不要求编写代码；选择单张表后，请求参数对应 `WHERE` 字段，返回参数对应 `SELECT` 字段，平台自动生成查询语句。它支持请求／返回参数批量选择、返回格式、缓存和分页配置。[火山引擎 DataLeap：API 开发—向导式](https://docs.volcengine.com/docs/6260/127699?lang=zh#_4-2-%E5%90%91%E5%AF%BC%E5%BC%8F)

**项目已定／设计建议**：本项目低代码首期只允许一张 ADS 逻辑表，输入应包含：

- 与传统开发共用的服务基本信息和运行约束；
- 单张 ADS 逻辑表；
- 请求条件字段、操作符、是否必填、默认值和样例；
- 返回字段、字段别名、排序顺序；
- 分页、最大返回行数和缓存；
- 平台生成的接口路径、请求／返回 Schema 和测试样例。

首期不要在低代码入口提供自由 Join、子查询、任意函数或自由 SQL 片段；否则低代码查询模型会退化成隐藏的脚本编辑器，难以稳定校验和回显。

### 5.2 编辑体验

低代码必须保持表单和可视化交互：

- 字段选择和拖动排序；
- 条件构造器，按字段类型限制可用操作符；
- 实时展示请求参数、返回 Schema 和只读 SQL 预览；
- 分页、排序、缓存等结构化配置；
- 对敏感字段、无权限字段和不兼容操作符就地提示。

**设计建议**：平台内部保存结构化 `LowCodeQueryModel`，SQL 是由它生成的派生物。若只保存生成后的 SQL，后续很难可靠地回到字段勾选界面，也无法区分用户配置和生成器行为。

### 5.3 校验

低代码入口级校验包括：

- 只选择一张已授权 ADS 逻辑表；
- 至少一个返回字段；
- 条件操作符与字段类型兼容；
- 参数名唯一，字段映射完整；
- 排序和分页配置合法；
- 不允许选择超出运行数据权限拟申请范围的字段。

生成 SQL 后仍必须执行与传统开发相同的公共 SQL、安全、资源、契约和测试校验。低代码只能减少用户编写错误，不能免除底层查询和数据权限校验。

### 5.4 转换边界

推荐采用以下规则：

- **低代码转传统**：允许，但必须显式执行“转为 SQL 开发”；创建新的草稿修订，保留服务标识、来源、契约和测试用例，冻结原低代码模型用于审计；
- **传统转低代码**：默认不允许。只有解析器能够证明 SQL 完全落入单表低代码表达能力时，才可提供试验性转换，并要求用户确认；
- 一旦手工修改了由低代码生成的 SQL，当前实现表达应切换为 `SQL_TEMPLATE`，不能继续假装能够无损回显低代码表单。

### 5.5 测试、版本和上线

低代码使用统一测试、版本和上线流程。测试页面不应因为其“无代码”而缩减：仍需支持表单／JSON 请求、Dry Run、结果、日志、状态、耗时和保存测试样例。

## 6. Coding Agent 辅助开发

### 6.1 官方证据能证明什么

目前没有找到与本项目完全对应的官方数据服务产品，能够证明 Coding Agent 已经可以在数据中台中生成 SQL API、数据权限、OpenAPI 契约并自动进入上线流程。因此下述产品方案均为**本项目设计推断**。

可作为安全边界依据的一手事实包括：

- GitHub 官方文档要求用户像审查任何贡献者一样审查 Coding Agent 产生的变更；Agent 创建的拉取请求必须由人审查和合并，Agent 自身不能把拉取请求标为可评审、批准或合并。[GitHub Docs：Review output from Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/review-copilot-output)、[GitHub Docs：Risks and mitigations for GitHub Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)
- NIST 的 DevSecOps 材料指出，AI 生成内容应由人监控和验证，需要可验证流程保证准确性和可信度；还应追踪模型、修改和注释，使 AI 辅助修改接受与人工修改相当的审查。[NIST NCCoE：The Role of AI in Software Development](https://pages.nist.gov/nccoe-devsecops/introduction.html#the-role-of-ai-in-software-development)、[NIST DevSecOps Reference Model：Artificial Intelligence](https://pages.nist.gov/nccoe-devsecops/notational-reference-model.html#artificial-intelligence)
- NIST SP 800-218A 不区分人工和 AI 生成代码，前提是所有源代码在使用前都必须接受漏洞及其他问题评估。[NIST SP 800-218A](https://www.nist.gov/publications/secure-software-development-practices-generative-ai-and-dual-use-foundation-models-ssdf)

上述材料证明了“生成后必须人审、可追踪、经过同等安全验证”的模式，但没有证明某个现成官方产品已经实现本项目需要的 API 草稿对象和上线审批。

### 6.2 输入

**设计建议**：Coding Agent 创建会话时，应由开发者显式选择或确认以下上下文，Agent 不得自行扩大范围：

- 当前租户、项目／业务域和目标服务草稿；
- 允许读取的 ADS 逻辑表及字段元数据；
- 自然语言业务需求、输入样例和期望输出；
- 接口方法、路径、分页、QPS、limit、缓存等约束；
- 需要生成或修改的范围：SQL、参数、返回契约、OpenAPI、测试用例；
- 目标实现表达：传统 SQL 草稿或低代码查询模型。

Agent 默认只读取元数据、数据字典、已有契约和经脱敏的受控样例。它不应获得生产数据库凭证、消费应用密钥或未经授权的数据样本。

### 6.3 编辑体验

Coding Agent 页面不能只有聊天框。必须同时提供：

1. 对话和需求澄清区；
2. Agent 当前可访问的来源和权限范围；
3. 结构化“变更提案”，按来源绑定、SQL、请求参数、返回参数、OpenAPI 和测试用例分组；
4. 与当前草稿的差异对比；
5. 逐项接受、拒绝和修改；
6. 接受后进入传统或低代码编辑器继续人工编辑；
7. 生成依据和风险提示，例如使用了哪些表、字段、关联条件和假设。

Agent 对已有草稿的操作应生成 Patch，不得无提示覆盖当前草稿。每次接受 Patch 都形成新的草稿修订，并记录开发者身份和 Agent 生成溯源。

### 6.4 Agent 专属校验和权限边界

除公共校验外，Agent 入口应增加以下强制控制：

- Agent 只能在开发者当前已授权的 ADS 资产范围内检索和生成；
- 新增表、字段或扩大数据范围必须先由开发者重新选择，不能由 Agent 自动取得权限；
- Agent 不能创建或读取生产凭证，不能调用生产 API，不能修改线上版本；
- Agent 不能发起上线申请、代替开发者确认测试结果、执行审批、上线或下线；
- Agent 输出必须经过与人工 SQL 相同的语法、参数绑定、注入风险、数据权限、资源、OpenAPI 和测试校验；
- Agent 生成的 `${}`、自由表名／字段名、无条件全表扫描、超大 limit、敏感字段输出等应作为高风险项阻止采纳或要求显式修正；
- 平台应记录模型标识、生成时间、发起人、授权上下文、输入来源范围、提案差异、采纳／拒绝结果和后续人工修改；原始提示如可能含敏感信息，应按专门保留策略脱敏或受限保存。

### 6.5 强制人工检查点

推荐至少设置三个不可由 Agent 代行的检查点：

1. **采纳检查点**：开发者查看差异并逐项接受 Agent 提案；
2. **测试检查点**：开发者亲自运行或确认指定测试用例，查看真实结果、日志和数据范围；
3. **提交检查点**：开发者确认来源、契约、运行权限申请范围及生产配置后，亲自提交上线审核。

管理者之后仍按统一上线审核检查服务契约、ADS 来源、运行数据权限和生产配置。Coding Agent 不能缩减管理审核。

## 7. 三种入口共用的服务草稿

### 7.1 推荐草稿结构

```text
APIServiceDraft
├─ Identity             服务标识、名称、负责人、分类、描述
├─ SourceBindings       ADS 逻辑表及开发权限快照
├─ Implementation       SQL 模板或低代码查询模型
├─ RequestContract      方法、路径、请求参数与 Schema
├─ ResponseContract     返回字段、错误、分页与 Schema
├─ OpenAPIContract      机器可读接口契约
├─ RuntimePolicy        limit、超时、缓存、QPS、安全方案
├─ RuntimeDataScope     拟申请并固化到服务版本的数据范围
├─ TestSuite            用例、样例、预期和最近执行证据
├─ ValidationReport     公共校验及入口级校验结果
└─ Provenance           人工／低代码／Agent 生成与修订记录
```

OpenAPI 官方规范把 HTTP API 定义为与编程语言无关的机器可读描述，可以表达路径、操作、参数、响应和安全方案，也可用于文档、代码生成和测试工具。[OpenAPI Specification 3.1.1](https://spec.openapis.org/oas/v3.1.1.html)

**设计建议**：OpenAPI 是 `APIServiceDraft` 的公共契约输出，不是传统开发页面的附属文件。低代码和 Coding Agent 同样必须实时生成并通过相同校验。

### 7.2 哪些内容必须共用

| 能力 | 必须共用的原因 |
|---|---|
| 服务身份 | 同一个服务不能因更换编辑入口产生新的集市产品 |
| ADS 来源绑定 | 数据层级、租户和数据权限约束与开发入口无关 |
| 请求／返回契约 | 消费者只关心接口，不应感知是 SQL、低代码还是 Agent 生成 |
| OpenAPI | 统一文档、测试、SDK 和网关配置的机器契约 |
| 运行策略 | QPS、limit、缓存、认证和超时由平台统一治理 |
| 测试套件 | 入口切换后仍需证明相同行为 |
| 版本 | 同一服务按契约和实现变化形成版本，不按入口分版本体系 |
| 上线／下线 | 统一执行版本发布、生产部署和集市可见性变化 |
| 审批 | 管理者审核对象是服务版本、数据范围和生产配置 |
| 授权和运维 | 服务上线后开发来源不再影响消费授权和运行指标 |

### 7.3 哪些交互必须保持差异

| 环节 | 传统开发 | 低代码开发 | Coding Agent |
|---|---|---|---|
| 主输入 | SQL／Dynamic SQL、表和参数 | 单表、条件、字段、排序、分页 | 自然语言意图、受控上下文和目标修改范围 |
| 主编辑器 | 代码编辑器 | 字段／条件构造器 | 对话＋结构化变更提案＋Diff |
| 实现真源 | SQL 模板 | 低代码查询模型 | 接受后落入 SQL 模板或低代码模型 |
| 专属校验 | SQL 语法、模板、绑定、只读性 | 字段类型、操作符、模型完整性 | 权限范围、生成风险、变更溯源、人工采纳 |
| 解释方式 | 开发者直接阅读 SQL | 展示字段到 SQL／契约的映射 | 展示假设、来源、生成差异和风险 |
| 人工确认 | 保存和测试 | 保存和测试 | 先逐项采纳，再保存和测试 |

## 8. 统一校验、测试、版本和上线流程

### 8.1 公共开发流水线

```text
选择入口
  ↓
创建／打开同一 API 服务草稿
  ↓
入口专属编辑与入口级校验
  ↓
公共校验：来源权限 → 实现安全 → 参数／响应契约 → OpenAPI → 资源策略
  ↓
Dry Run
  ↓
测试环境执行与测试证据
  ↓
开发者确认并提交上线审核
  ↓
管理者审核服务版本、ADS 来源、运行数据权限和生产配置
  ↓
上线：版本发布 → 生产部署 → 服务集市可见
```

入口专属校验和公共校验是不同阶段，但不建议增加大量用户可见生命周期状态。草稿详情中显示“校验未通过／待测试／测试通过”等质量门禁即可；对外主状态仍使用本项目已经确认的：

```text
草稿 → 待上线审核 → 上线中 → 已上线
     → 待下线审核 → 下线中 → 已下线
```

### 8.2 测试模型

**官方事实**：DataLeap 脚本／向导测试支持 Dry Run、表单或 JSON 请求、参数值和安全等级设置；结果区域展示结果、请求日志、请求参数体、状态、耗时和数据大小，并允许将参数同步为调用示例。Dry Run 只返回 SQL 逻辑而不执行。[火山引擎 DataLeap：测试 API](https://docs.volcengine.com/docs/6260/127699?lang=zh#_6-%E6%B5%8B%E8%AF%95-api)

**设计建议**：三种入口共用同一测试工作台和 `TestSuite`，至少支持：

- Dry Run：只解析最终 SQL、参数和权限，不读取真实结果；
- 功能测试：表单／JSON 请求，查看结果、错误、日志、耗时和返回大小；
- 边界测试：必填缺失、空值、数组、最大 limit、非法操作符和无结果；
- 安全测试：注入样例、越权字段、超范围数据和敏感返回；
- 回归测试：新版本与已上线版本复用测试用例并对比契约／Schema；
- 测试证据：保存用例版本、请求快照、结果摘要、执行环境、执行者和时间。

Coding Agent 可以生成候选测试用例，但不能把“生成了用例”视为“测试通过”。真实执行及其结果必须由平台测试能力产生。

### 8.3 版本模型

**官方事实**：DataLeap 初始版本默认为 V0；保存可以更新当前非线上版本，也可以另存为新版本或新 API；线上版本不允许直接保存。版本列表支持查看配置、发布环境、下线、删除未发布版本和比较两个版本。[火山引擎 DataLeap：保存 API／版本信息](https://docs.volcengine.com/docs/6260/127699?lang=zh#_5-%E4%BF%9D%E5%AD%98-api)

**设计建议**：

- 草稿可以保存多次修订；
- 进入上线审核时冻结候选版本内容和运行数据权限申请范围；
- 已发布版本不可变，任何修改都从它派生新草稿版本；
- 版本比较必须覆盖来源、SQL／低代码模型、请求／返回契约、OpenAPI、运行配置、数据范围和测试证据；
- `authoringOrigin` 和 Agent 溯源进入版本审计，但不改变消费者看到的服务版本语义。

### 8.4 环境和上线

**官方事实**：DataLeap 测试环境发布无需审核；线上环境是否触发审批取决于项目配置。线上发布可以展示审批流程、通知人、发布原因；线上下线也可以按项目配置触发审批。[火山引擎 DataLeap：发布 API／版本信息](https://docs.volcengine.com/docs/6260/127699?lang=zh#_7-%E5%8F%91%E5%B8%83api)

**项目已定**：本项目对生产上线和下线统一要求管理者审核。建议：

- 测试环境部署允许开发者在权限范围内直接执行；
- 生产上线由开发者亲自提交；
- 审批对象为冻结的候选服务版本、ADS 来源、运行数据权限和生产配置；
- 审批通过后系统执行版本发布、生产部署和服务集市可见性生效；
- 无论草稿由哪个入口创建，都不得跳过这条链路。

## 9. 原型应呈现的关键页面和交互

### 9.1 新建 API

展示三张开发入口卡片，并明确能力边界：

- 传统开发：复杂 SQL／Dynamic SQL，多表；
- 低代码开发：单表字段和条件配置；
- Coding Agent：通过需求描述辅助生成可审查草稿。

三个入口提交后进入同一种服务详情框架，不创建三套导航。

### 9.2 共用详情框架

建议二级页签：

```text
开发配置｜接口契约｜测试｜版本｜授权｜运行数据｜操作记录
```

“开发配置”内部按当前实现表达和创作入口切换专属编辑器；其余页签共用。

### 9.3 传统开发原型重点

- ADS 逻辑表和字段树；
- 普通 SQL／Dynamic SQL 切换；
- 参数解析、格式化、校验、Dry Run；
- 请求／返回参数表；
- OpenAPI 和最终 SQL 预览；
- 测试结果、日志和耗时。

### 9.4 低代码开发原型重点

- 单张 ADS 逻辑表；
- 请求条件、操作符、返回字段、排序和分页；
- 自动生成的只读 SQL 与 OpenAPI 预览；
- “转为 SQL 开发”的单向转换提醒；
- 与传统开发相同的测试工作台。

### 9.5 Coding Agent 原型重点

- 对话区和当前可访问数据范围；
- 澄清问题和生成计划；
- SQL、参数、契约和测试用例分组 Diff；
- 逐项接受／拒绝；
- “接受并进入人工编辑”，而不是“自动上线”；
- Agent 生成溯源、风险提示及强制人工测试、提交状态。

## 10. 对后续规格的明确建议

1. 正式规格中把“三种开发方式”命名为“三种创作入口”，避免误导为三套服务生命周期。
2. 将 `implementationRepresentation` 与 `authoringOrigin` 分开建模。
3. 低代码首期仅支持单张 ADS 逻辑表；结构化查询模型是真源，SQL 是派生物。
4. 低代码转 SQL 允许且单向；传统 SQL 默认不能无损转回低代码。
5. Coding Agent 首期只操作草稿并产生 Patch；不允许自动取得权限、自动测试通过、自动提交或上线。
6. 三种入口统一生成 OpenAPI，并共享测试套件、测试证据、版本比较、上线审核、授权和运维。
7. Dynamic SQL 优先使用 `#{}` 类型化参数；`${}` 仅用于白名单标识符等受控场景。
8. 把“开发者人工采纳 Agent 变更、人工确认测试、人工提交上线”写成不可绕过的业务规则。

## 11. 仍需后续决策的问题

以下问题已经被研究结果明确到可以进入 Wayfinder 决策，但本工单不代替用户作答：

1. 传统开发首期是否允许同源多张 ADS 逻辑表；最大张数由产品固定还是由查询引擎适配器提供；
2. Dynamic SQL 的 `${}` 是否首期完全禁用，还是只对白名单表名／字段名开放；
3. 低代码是否首期支持聚合函数、分组和字段别名；
4. 低代码转传统后，是覆盖当前草稿修订还是自动创建新草稿版本；
5. Coding Agent 首期只生成 SQL 草稿，还是同时支持生成低代码查询模型；
6. Agent 测试时是否允许访问脱敏数据样本，或只允许元数据和 Dry Run；
7. 测试环境部署是否需要独立权限或轻量审批；
8. 上线审核的强制门禁：至少几个测试用例、是否要求安全测试、是否要求与上一线上版本契约对比。
