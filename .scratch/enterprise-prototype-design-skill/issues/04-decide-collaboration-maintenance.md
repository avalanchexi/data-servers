# 确定 Skill 的多人协作与维护方式

Type: grilling
Status: resolved
Parent: ../map.md
Blocked by: 02

## Question

确定多人协作时谁可以修改原型设计规范 Skill、变更如何评审、如何记录来源版本和项目级调整、如何避免 `SKILL.md` 与参考资料重复或分叉，以及未来从源设计系统吸收更新时采用人工挑选、差异审计还是其他同步方式；同时明确自动触发描述和显式调用名称的稳定性要求。

## Answer

原型设计规范 Skill 采用“仓库内唯一事实来源、认领后修改、人工选择性同步、评审验证后生效”的多人协作方式。

1. **唯一事实来源**：`.agents/skills/enterprise-prototype-design/` 中已提交的内容是当前项目唯一有效版本。桌面源设计系统只用于首次迁移和后续人工比对，不允许通过个人绝对路径、软链接或运行时读取形成依赖。
2. **修改权限**：任何协作者都可以提出变更；开始修改前必须在本地 Markdown 跟踪器中建立或认领一张范围明确的工单。并行工作不得同时修改同一规则文件，发生重叠时以已认领工单和 Git 差异为协调依据。
3. **评审方式**：Skill 变更必须作为独立、可审查的 Git 差异提交，不与无关产品文档或原型改动混合。至少由一名未参与该变更的协作者检查触发边界、规则唯一性、HTML 行为、品牌清理和必要验证结果后才视为生效。
4. **规则唯一位置**：`SKILL.md` 只定义触发、工作流、按需读取路由和硬约束；每条详细规则只存在于一份对应 reference；精确数值只以 `assets/design-tokens.css` 为机器事实来源，reference 解释其用途但不维护第二套数值表。
5. **项目入口**：`AGENTS.md` 只增加何时使用 `$enterprise-prototype-design` 及其仓库路径的简短入口，不复制设计规则。数据服务平台领域中的 `Skill` 继续表示平台产品；协作文档始终使用完整名称“原型设计规范 Skill”区分二者。
6. **来源记录**：在 Skill 内维护一份仅供维护者按需读取的 `references/provenance.md`，记录首次提炼日期、上游技术来源、固定提交号、各来源被用于哪些规则，以及项目级品牌中立化调整。技术来源信息不得进入生成的 HTML 或普通示例。
7. **更新方式**：不自动同步整个源目录。需要吸收更新时，先以来源提交号或快照做差异审计，再人工挑选会改变当前 HTML 原型决策的内容；按 `design-tokens.css → 对应 reference → 路由或示例验证` 的顺序更新。React 实现、完整 UI Kit、构建环境和品牌展示始终不随更新进入仓库。
8. **稳定接口**：Skill 名称 `enterprise-prototype-design`、目录和显式调用 `$enterprise-prototype-design` 视为稳定接口。其 description 应只匹配“设计、生成、修改或审查桌面 Web HTML 原型”，不自动匹配生产前端实现、React 组件开发、普通文档写作或数据服务平台中的 Skill 产品设计。
9. **元数据最小化**：默认依靠 `SKILL.md` description 自动触发；只有粗稿验证表明 UI 展示名、默认提示或调用策略确有价值时才增加 `agents/openai.yaml`，不提前创建无用途的元数据。
10. **变更验证**：所有变更至少通过 Skill 结构验证、禁止品牌内容扫描和一项代表性 HTML 行为检查；更完整的自动化边界在 Skill 粗稿形成后确定。Git 历史和工单答案承担变更记录，不额外维护重复的 README 或 CHANGELOG。
