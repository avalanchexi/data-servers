# 验证 AI 服务开发与数据应用装配

Type: prototype
Status: resolved
Parent: ../map.md

## Question

如何用一个首版离线交互原型验证 API、Agent、MCP、Skill、Worker 独立开发上线，AI 只修改草稿修订，以及数据应用在应用接入层、服务能力层和数据权限层中选择固定服务版本的核心范式？

## Answer

已交付单文件离线原型 [`prototypes/ai-service-development.html`](../../../prototypes/ai-service-development.html)。2026-08-28 用户选择方案 C「服务制品流水线」作为主方案；正常打开和原有 `?variant=C` 链接均直接进入 C 且不显示原型切换器。历史 A／B／C 只在 `?compare=1&variant=A|B|C` 显式比较模式中保留：

1. 方案 A「列表与专属编辑器」：以服务目录为入口，进入 Agent 整体制品编辑器；适合强调管理效率与专业开发深度。
2. 方案 B「AI 任务工作台」：以开发任务会话、模型／MCP／Skill 上下文和待采纳变更集为入口；适合验证 AI-first 开发体验。
3. 方案 C「服务制品流水线」：按草稿修订、仿真测试、上线审核和已上线组织服务卡片；适合强调全局生命周期治理。

选型落点是优先表达“服务独立开发—测试—审核—上线—供数据应用选择”的已确认范式；Agent 专属编辑器保留为服务卡片的下钻工作区，数据应用三层装配保留为独立业务视图。A／B 不再作为正常产品入口。

三种方向共享同一领域语义和交互样例：Agent、MCP、Skill、Worker 原生开发，AI 只生成待人工采纳的草稿变更，草稿修订与正式版本分离，人工仿真测试和提交上线审核，以及数据应用按应用接入层、服务能力层、数据权限层装配固定服务版本。API 保留独立开发入口并可被数据应用选择，本轮不重复展开其既有开发编辑器。

参考 `HiMarket-开发者端功能与能力说明.docx` 吸收了能力类型导航、简洁搜索筛选、开发会话栏和模型／MCP／Skill 上下文选择，不复用其品牌、视觉装饰、CLI 或消费门户结构。

首版曾完成内联 JavaScript 语法与关键交互钩子检查、零远程依赖和品牌中立扫描、`git diff --check`，并以 1440×900 真实 Chromium 渲染检查 A、B、C 三个入口。该视觉结论仅对应首版，后续修改的验证范围见下方逐次记录。

2026-08-28 当前实现已扩展为四类型专属详情：所有 AI 服务均有数据需求，托管服务可继续开发，非托管服务只登记需求。所有提交先进入审核，非托管审核不产生可部署服务版本，也不替代数据应用注册和授权。类型字段调研、落地清单和边界见 [`docs/research/ai-service-development-configurations.md`](../../../docs/research/ai-service-development-configurations.md)。
