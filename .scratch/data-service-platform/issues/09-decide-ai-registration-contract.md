# 确定外部数据消费方登记与统一网关边界

Type: grilling
Status: open
Parent: ../map.md
Blocked by: 02

## Question

Agent、MCP、模型、Skill、Worker 通过统一网关注册时需要哪些统一字段和类型专属契约，注册审核、技术注册、数据服务同步与上线生命周期如何衔接，以及 HiMarket 参考逻辑应在哪个适配边界终止？

## Answer


## Comments

### 2026-08-27 第一轮确认

- “注册”专指外部数据消费场景已经拥有、并非由平台开发的 Agent、模型、MCP 等服务通过注册纳入管理，不指用户账号注册。
- 外部注册产品与平台原生产品暂不建模为同一种产品。
- API、Agent、MCP、模型、Skill、Worker 首期全部支持平台原生开发；平台负责托管和实际运行。
- AI 只生成或修改草稿、代码、契约、测试和文档等内容，不执行测试、提审、审批或上线。
- 采用统一“服务开发”入口，下设 API 开发与 AI 服务开发；数据应用不再承载 AI 注册入口。
- 数据应用只能选择已上线、可见的具体服务版本，不自动跟随最新版。
- 服务上线审批与数据应用版本／授权审批保持独立。
- 注册审核与上线审核职责不同：注册审核决定外部对象能否进入服务开发平面；上线审核的精确对象和触发时点仍需在后续轮次澄清。
- 待澄清：外部注册产品在“全部平台托管”约束下是迁移制品到平台运行，还是保留外部运行时并由平台代理；“模型原生开发”是否包含训练；注册产品的修改、测试、发版与数据应用管理之间的先后关系。

### 2026-08-27 第二轮确认

- 外部注册产品完成注册审核后，先进入服务开发平面完成修改、测试与发版准备，再独立提交服务上线审核；上线并进入服务集市后，数据应用才选择具体版本并进入应用版本／授权审批。
- 外部注册产品与平台原生产品始终保留不同领域身份，但上线后进入同一服务集市并采用相同的数据应用选择方式。
- 外部注册产品默认私有，可以另行申请转为租户内共有。
- 外部注册产品暂时由管理角色人员负责开发平面及生命周期操作。
- 各服务类型共用开发外壳，但使用类型专属编辑器和契约。
- MaaS 中台管理用于服务开发的 Agent 及其线程、提示词、模型中转、费用、并发和用户访问；数据服务平台使用该 Agent 生成 API、Agent、MCP、模型、Skill、Worker 等服务内容。
- 创建服务时声明对数据资产、API、MCP 和 Skill 的依赖；服务版本固定依赖，上线和数据应用授权均需要审查依赖闭包。
- 新冲突：用户提出自有 Agent、MCP 可以“以数据应用形式”托管；这与 ADR-0001 中数据应用仅作为外部消费场景和调用身份的边界可能冲突，需先区分“自有能力消费平台数据”与“将自有能力发布给其他数据应用复用”。

### 2026-08-27 第三轮确认

- 自有 Agent、MCP 需要同时覆盖内部使用与外部使用，但“内部／外部”目前尚未明确是运行位置、可见范围还是复用对象，需要继续拆分。
- 服务开发形成的全部正式制品归属数据服务平台；MaaS 只提供开发 Agent 及相关运行能力。
- 服务依赖必须显式声明、随版本固定并禁止循环。
- MCP 可以依赖数据资产、API，并可能依赖 CLI 执行能力；CLI 是开发工具、受治理运行能力还是可发布产品仍待澄清。
- Skill 可以依赖 API、MCP、脚本和数据资产。
- 模型服务暂不需要纳入下游服务依赖矩阵；这是否同时缩减“模型原生开发”范围仍待确认。

### 2026-08-27 第四轮确认

- 数据应用的运行位置和服务复用目的采用两个独立维度：数据应用可以平台托管或外部运行；自用制品保留为数据应用运行内容，需要供其他数据应用复用时从同一制品创建独立服务产品，数据应用对象本身不进入服务集市。
- 模型只通过 AI 网关注册管理，用于外部数据消费的合法合规治理；首期不提供模型原生开发工作台。
- 数据权限只向数据应用授权，即只向具体数据消费场景授权；服务产品和服务版本只声明数据依赖与所需范围，不持有运行数据权限。
- Agent 可以包含 Tools、Memory、Prompt 等内容，平台托管时全部约束在数据应用沙箱内。
- 底层组件的操作可能被开发为 CLI 供 Agent 使用；CLI 的产品身份、制品形态和授权模型仍待决定。

### 2026-08-27 第五轮确认

- CLI 是后续可能建设的能力，首期不纳入依赖类型、产品类型或运行契约。
- 每个数据应用只选择一种主要消费形态，内部仍可装配多个服务。
- 平台托管数据应用需要类似 API 的开发、审核和上线过程，但“类似”是否复用服务产品状态机及是否进入集市仍需继续明确。
- 模型可以暂不考虑；保留 AI 网关注册与合法合规治理方向，本次不展开模型开发、上线和集市生命周期。
- Tools、Memory、Prompt 等内容统一作为 Agent 整体管理，不再拆成 Agent 内部的独立部分；Agent 整体受数据应用沙箱约束。

### 2026-08-27 第六轮确认

- 数据应用中的自用制品原则上不复用、不转换为共享服务产品；确需供其他数据应用使用时，独立创建或注册服务产品。
- Agent 合法使用 MCP 的前提是 MCP 已在 AI 网关注册并进入治理范围；未注册 MCP 不允许被 Agent 直接装配或调用。
- 待澄清：一个需要访问平台数据、同时又被 Agent 调用的 MCP，是否必须同时拥有“注册 MCP 产品身份”和“数据应用消费身份”。
- 待回答：平台托管数据应用是否采用独立于服务产品的上线状态机；Agent 整体审核是否仍展示其依赖与敏感权限。
- 平台托管数据应用采用与 API 类似但独立的开发、测试、上线审核、部署、运行和下线状态机；它不进入服务集市。
- Agent 作为一个整体制品提交审核，但审核详情必须展示数据、模型、API、MCP、Skill 等依赖，以及敏感权限、Memory 策略和沙箱范围。

### 2026-08-27 第七轮部分确认

- 依赖注册采用风险触发边界：能力只要获取平台数据、形成对外数据通道，或对中台执行实质性操作，即必须完成注册和治理。
- 纯本地、无平台数据、无外部通道且不改变中台状态的辅助能力不强制成为服务集市产品，但仍受版本、沙箱和审计约束。
- 外部运行的数据消费场景通过数据应用注册纳入身份、权限、凭据和审计治理；数据应用注册不等于服务注册、服务上线或已经取得数据权限。
- 待澄清：外部 Agent 调用受管 MCP 时，如何把外部 Agent 映射为数据应用身份并透传数据权限。
- 待回答：自用制品是否允许显式复制为完全独立的新服务草稿。

### 2026-08-27 第八轮确认

- 外部 Agent 先注册为 Agent 形态的数据应用；调用受管 MCP 时透传该数据应用身份，MCP 最终只能使用调用方数据应用获批的数据权限。
- 数据应用先完成注册审核并形成应用身份，再分别申请数据权限、服务授权和必要操作权限；全部批准并完成凭据、网关策略下发后生效。
- 允许人工将自用制品一次性复制为独立服务草稿；新产品拥有独立身份、版本、测试、审批和生命周期，复制后不自动同步。
- 对中台执行实质性操作的能力先注册为受管依赖；数据应用按动作申请操作权限，每次调用透传应用身份并审计，高风险或破坏性操作增加人工确认。

### 2026-08-27 第九轮确认

- Agent 原生开发形成包含运行配置、输入输出契约、依赖、Tools、Memory、Prompt、测试和文档的整体制品，并整体版本化。
- MCP 原生开发形成遵循 MCP 协议的可托管服务制品；外部地址登记只属于注册路径。
- Skill 形成版本化能力包，除供平台 Agent 沙箱使用外，也可以按固定版本交付外部 Agent。
- Worker 形成具有任务输入输出、触发、超时、重试、资源限制和失败恢复语义的独立可部署制品，不与 Agent 共用运行模型。
- 所有原生开发类型均支持自然语言生成结构化草稿和人工专属编辑器两种方式。
- 公共质量门禁暂不深入设计；保留人工确认、基本可审核性和类型协议必要测试原则。

### 2026-08-27 第十轮部分确认

- 外部数据消费场景使用 Skill 时，与 MCP、API 采用相同的数据应用身份、授权审核和固定版本治理；具体技术交付是下载包还是远程调用仍需明确。
- 外部注册的 API、Agent、MCP、Skill 等能力运行在中台之外，需要在数据应用中建立映射、取得授权审核，并注册到 AI 网关。
- 最新表述要求一项外部注册能力对应一个数据应用；能力审核通过、完成数据应用关联且数据应用审核通过后才允许使用。
- 该“一能力对应一数据应用”的模型与此前确认的“外部注册产品上线后进入统一服务集市、可由其他数据应用选择”冲突，必须明确外部注册对象究竟是应用专属能力还是可复用服务产品。
- 用户对本轮“发现方式”的回答转向了审核和关联前提，自动发现／人工登记的入口优先级尚未决定。
- Worker 首期触发方式、Agent 同步／异步调用模式尚未回答。
- Worker 首期支持 Agent／API 按需异步任务和平台定时触发，事件流触发后续再扩展。
- Agent 版本可以声明同步会话、异步任务或两者兼有，数据应用按固定版本的已批准契约调用。

### 2026-08-27 第十一轮确认

- 外部注册对象最终建模为数据应用专属的“外部注册能力”，不是服务产品，不进入服务集市，也不能被其他数据应用选择。
- 每项外部注册能力只属于一个数据应用；一个数据应用可以登记多项外部 API、Agent、MCP、Skill、Worker 等能力，共享该应用的身份、权限、配额和审计边界。
- 外部能力运行在中台之外，通过 AI 网关或 API 网关纳入治理；当前由管理者在创建和维护数据应用时登记并建立映射，不开放外部用户自助入口。
- 外部场景自有 Skill 可能包含数据获取脚本，因此与 Agent、MCP 一样作为应用专属外部能力管理，而不是仅按下载包处理。
- 顺序固定为：创建数据应用草稿 → 登记外部能力并映射应用 → 能力审核及网关注册 → 数据／服务／操作授权 → 数据应用整体审核 → 凭据和策略下发 → 生效。
- 所有向外部提供平台数据，或允许外部对中台执行直接实质操作的对象，都必须经过统一网关中的 API 网关或 AI 网关治理，不允许旁路直连。
- 此决定取代前几轮“外部注册产品上线后进入统一服务集市”的暂定方向；可复用能力只能通过独立的平台原生服务开发、测试、上线和集市流程形成。

### 2026-08-27 第十二轮确认

- 服务开发入口、对象权限与操作审计复用平台基座的统一角色权限和审计服务；具备开发岗位权限的人员可以使用平台原生服务开发。
- 开发 Agent 只能读取当前草稿、当前开发者已授权的数据资产元数据、已批准依赖和平台受控样例／规范，不能读取未授权生产数据、其他草稿或秘密值。
- AI 生成或修改的内容保存为可追溯的草稿修订并纳入版本管理，不覆盖已发布版本。
- 外部能力注册采用完整最低信息集，覆盖所属数据应用、类型、来源与外部标识、版本、端点或制品、契约、认证引用、数据通道、中台操作、运行位置、责任、测试及合规信息，秘密值不明文落库。
- 创建人与审批人是否隔离及审批人资格由平台统一工作流引擎管理，数据服务平台不硬编码职责分离规则。

### 2026-08-27 第十三轮确认

- 同一外部技术服务原则上不能被多个数据应用直接共享；只有它具备独立租户或客户端、运行身份、认证凭据和数据隔离时，才允许为不同数据应用分别创建应用专属注册记录。
- 外部能力注册记录以“来源系统 + 外部对象标识 + 外部版本 + 数据应用”确定身份，访问 URL 只是可变访问位置，不作为能力唯一标识。
- 输入输出、工具、数据通道、操作范围或认证身份变化时创建新的外部能力版本，重新执行测试、能力审核、数据应用版本更新、应用审核和策略下发；切换前原版本保持有效，不允许原地覆盖。
- 外部能力停用后，网关立即阻断该能力的新调用；主要消费入口停用使数据应用进入已暂停，非关键附属能力停用使其进入降级，恢复或替换后重新测试并下发相关策略。
- 外部能力由管理员在数据应用内手工发起登记；平台按类型解析 OpenAPI、MCP 信息与工具清单、Agent 描述与契约、Skill 包与脚本声明、Worker 任务与运行清单并进行探测，但必须由管理员确认，首期不自动扫描外部环境。
- API 进入 API 网关，Agent、MCP、Skill、Worker 进入 AI 网关；一个对象同时涉及两种协议时可以经过两个网关，但共享同一数据应用身份、注册标识、授权结果和审计链路，不形成两套独立权限。

### 2026-08-27 第十四轮部分确认

- 外部数据消费场景必须创建数据应用；数据应用关联已经注册到网关中的平台内部 API、Agent、MCP 等服务，只有数据应用审核上线后才能正常调用。该表述是否意味着不再单独建立“跨网关外部能力业务对象”，仍需与前几轮模型对齐。
- 外部能力在一定时间没有响应后应“终端”；这里是终止单次调用、停用该能力还是终止数据应用，尚需明确。
- 认证秘密轮换、证书续期或不改变身份和契约的地址变化不产生外部能力新版本，但会直接影响服务可用状态。
- 外部能力通过所属数据应用删除，数据应用为外部能力提供数据通道；删除是解除映射、停用归档还是物理删除，以及删除数据应用时的历史保留范围仍需明确。
- AI 先生成并展示代码、配置、契约、依赖和测试变更集；开发者可以全部接受、部分接受或拒绝，接受后才形成新的草稿修订。
- 开发测试只能使用模拟、仿真或脱敏数据，不能使用生产数据，也不能执行真实中台操作。
- 平台原生产品的责任主体继续由岗位角色与权限基础服务管理，本次不深入设计产品责任人模型。
- 数据应用升级服务版本“支持自动审计，但是支持手动回滚”；其中“自动审计”是否指自动升级、自动审批还是仅自动记录审计，尚需明确。
- 保留仍被数据应用使用的服务直接下线能力；下线前后的影响提示、调用处理和应用状态仍需明确。
- 外部 Agent 以 Skill 文件形式使用能力，文件中的脚本可以消费数据或执行操作；脚本如何取得数据应用身份、凭据及如何经过网关仍需明确。

### 2026-08-27 第十五轮确认

- 先前称为“外部能力”的对象本质是外部数据消费方；它与外部系统、外部消费场景和数据应用的准确关系需要进一步统一术语。
- 无响应超时终止本次同步调用或异步任务；连续失败达到阈值后把相关服务标记为不可用，但不自动删除或终止整个数据应用。
- 不产生新版本的运行配置变化采用“可用 → 验证中 → 可用／不可用”状态；验证失败后阻断新调用并允许修复或回退，过程记录审计但不改变服务版本或数据应用版本。
- 服务版本经审核后自动更新到新版本，新版本发布后支持回滚旧版本；这里的提交主体、审核对象和自动切换范围仍需明确。
- 服务直接下线前展示受影响应用并二次确认，但不因存在引用而阻止；下线后拒绝新调用，应用进入不可用或降级，进行中的调用和任务按超时策略处理，不自动切换其他版本。
- Skill 以签名固定版本文件交付外部 Agent，文件不得包含平台凭据；运行时注入数据应用短期凭据，脚本只能经 API 网关或 AI 网关在数据权限和动作级操作权限内执行。
- 开发测试使用模拟网关和仿真执行器，只读取模拟、仿真或脱敏数据；写操作仅返回预计变更、权限判定和调用轨迹，不改变真实中台状态。

### 2026-08-27 第十六轮确认

- 数据应用是外部数据消费方在平台中的映射；外部数据消费方通过数据应用取得身份、数据通道、权限、配额和审计边界。
- 数据应用选择服务新版本并重新提交应用版本审核，审核通过后平台自动完成版本更新；服务版本审核本身不直接更新引用它的数据应用。
- 调用无响应的超时和可用性阈值同时受中台设置与数据应用设置控制，两级设置的继承和约束方向仍需明确。
- Skill 停止分发或数据应用停用后，平台撤销短期令牌、服务授权和网关策略；已经下载到外部的文件无需物理收回，但不能继续合法取得平台数据或执行操作。
- 首期只保证外部 Skill 文件下载时的来源、固定版本和签名，运行阶段只按数据应用身份、数据权限和操作权限治理，不声称能够验证外部实际执行代码；代码级可信执行留待受信任沙箱或远程证明能力。

### 2026-08-27 第十七轮确认

- 正式取消独立的“外部注册能力、外部能力版本、外部能力审核”业务对象和状态机；已有外部 Agent、MCP、Skill、Worker 或普通客户端通过创建数据应用登记为外部数据消费方的主要技术形态，审核对象是数据应用。
- 一个外部数据消费方可以对应多个数据应用，但每个数据应用只映射该消费方的一个消费场景；需要独立权限、凭据、配额、版本或审计边界时拆分数据应用。
- 数据应用新版本审核通过后自动完成更新；允许直接回滚到曾经审核通过且仍满足服务在线、授权有效和当前安全策略的完整应用快照，否则阻止回滚并说明原因。
- 中台设置定义调用和任务超时的默认值与允许范围，数据应用可以在范围内设置更短的超时，未设置时继承默认值，不得放宽中台上限；连续失败后的全局服务可用状态由中台统一判定。
- 平台内部服务版本审核通过后，系统自动执行部署、网关注册和策略发布；全部成功后才标记已上线并允许数据应用选择，网关注册失败时保持上线失败。
- AI 或人工每次保存形成可恢复、可比较的草稿修订；只有开发者明确创建并提交上线审核时才形成不可变正式服务版本，草稿修订不能上线或被数据应用选择。

### 2026-08-27 第十八轮确认

- 数据应用不物理删除，而是通过审批流程执行停用和逻辑删除；停用后撤销凭据、授权和网关策略，保留历史版本、审批、调用和审计记录。
- 消费治理采用三层表达：底层为数据权限，中层为 Agent、MCP、Skill、API 等服务，上层为数据应用绑定的证书、密钥等接入身份；三层的正式名称、调用方向和“主要消费形态”所在层仍需统一。
- Skill 可以作为数据应用的主要消费形态；其与作为中层内部服务的 Skill 如何区分仍需明确。
- 一个内部服务跨 API 网关和 AI 网关时仍只有一个服务产品及服务版本，两个网关只保存共享身份、契约和审计关系的运行投影，不能分别授权或独立进入集市。
- 数据应用版本采用原子切换：切换后的新调用使用新应用版本，切换前已开始的同步调用和异步任务继续使用旧版本直到完成或超时；回滚采用相同规则。
