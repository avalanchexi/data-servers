# 数据服务功能模块 DCMM 4 级支撑能力评估

## 1. 技术结论

**结论：当前仓库不能证明所属组织已经达到 GB/T 36073—2025 DCMM 4 级（量化管理级），也不能证明“数据服务功能模块”已经形成生产级 DCMM 4 级支撑能力。**

仓库当前能够证明的是：

- 已形成较完整的数据服务域目标设计，包括服务生产、数据应用、授权、运行管理、审计和设置等领域约定；
- 已交付 3 份带内联 JavaScript 的离线 HTML 交互原型，并有 4 组 Node 回归测试；本次复核运行 `node --test prototypes/tests/*.test.cjs`，103 项全部通过；
- 原型能够演示服务生命周期、AI 辅助开发、运行指标、异常、结构化审计、认证策略和类型专属限制等产品支撑场景。

仓库同时明确排除了生产级后端、真实消息代理、正式系统建设、真实网关和生产部署（`.scratch/data-service-platform/map.md:40-47`）。运行指标文档也明确说明全部数值为离线示例，仅实现 HTML 展示和交互，未接认证、采集、持续刷新、长期存储或生产阈值（`docs/research/runtime-instance-metrics.md:7-10,75-79`）。因此：

1. 原型页面中的指标、报表、审计记录和“已上线”状态均不得视为真实运行证据；
2. 原型回归测试只证明离线原型脚本在测试替身中满足预期，不证明后端、网关、运行时、审计服务或组织管理过程已经实现；
3. DCMM 是组织数据管理能力成熟度模型。产品模块可以提供采集、控制、留痕、评估和报告支撑，但不能单独证明组织已建立量化体系、已定期评估并持续改进、已开展内外部审计或已参与国家/行业标准工作。

按本报告纳入的 47 个原子要求统计，当前仓库证据为：**满足 0、部分 20、缺失 24、无法从仓库证明 3**。其中“部分”只表示存在文档或原型级产品支撑，不表示 DCMM 条款已满足。

## 2. 评估口径与证据等级

### 2.1 评估对象

- **评估对象**：本仓库定义的“数据服务域”及其数据服务功能模块，不扩展评价数据治理、数据安全、数据质量、财务、人力或标准化组织的全部能力。
- **核心条款**：14.4 数据服务的 4 个要求。
- **直接相关条款**：只纳入与数据服务量化、AI、数据共享与元数据、资产权属/价值/运营、质量、安全、审计、设计开发、运维、数据应用和数据开放直接相关的 4 级要求。
- **比较基线**：当前仓库在 2026-08-28 可读取的文件与可执行测试；不推断仓库外系统、人员、制度或运行事实。

### 2.2 当前可证明与目标设计分列

- **当前覆盖**：只依据当前仓库可验证事实。目标术语、ADR 和研究文档不能提升为“已实现”；原型和原型测试不能提升为生产实现。
- **目标覆盖**：判断 `CONTEXT.md`、ADR、研究文档和已确认议题是否已经定义所需产品支撑能力。目标设计存在不等于能力已上线，也不等于组织条款已达成。
- **组织证据边界**：凡要求“组织层面”“定期开展”“形成报告”“持续改进”“引入外部机构”“参与国家标准/主导行业标准”的，必须补充制度、职责、真实周期数据、审批/执行记录、正式报告、外审材料或标准化活动证明。

### 2.3 覆盖判断

| 判断 | 含义 |
|---|---|
| 满足 | 仓库内已有足够的生产实现和真实运行/管理证据支撑该要求。 |
| 部分 | 仅覆盖要求的一部分，或证据只达到文档/原型层，尚缺生产实现或组织运行证据。 |
| 缺失 | 仓库未发现该能力的有效设计或实现证据，或现有内容与条款对象不同。 |
| 无法从仓库证明 | 条款主要要求组织行为、外部活动或周期性成效，仅凭产品仓库无法作出结论。 |

### 2.4 证据等级

| 等级 | 名称 | 本报告判定规则 |
|---|---|---|
| E3 | 实现 | 生产代码、持久化模型、接口、采集/执行适配器、部署配置，以及与真实依赖集成的测试或运行证据。当前仓库未发现数据服务域 E3 证据。 |
| E2 | 原型 | 可离线交互的 HTML/JavaScript 原型及其原型回归测试。只证明交互逻辑，不证明生产后端。 |
| E1 | 文档 | `CONTEXT.md`、ADR、研究文档、议题结论和规格约定。只证明目标或决策。 |
| E0 | 无证据 | 未发现与条款对象直接对应的仓库证据。 |

## 4. 七个一级功能的 DCMM 4 级支撑映射

### 4.1 七项口径与“服务开发”冲突

本节严格按用户指定的七个一级功能统计：**工作台、服务集市、数据应用、应用与授权、审批中心、运行管理、设置**，确保 7/7 均有显式结论。

仓库内部存在口径冲突，不能静默处理：

- `CONTEXT.md:15-17` 将数据服务域定义为七项功能，未列“服务开发”；
- `CONTEXT.md:51-56` 又将“服务开发”定义为独立的服务生产平面；
- `CONTEXT.md:361` 的导航约束列出工作台、**服务开发**、服务集市、数据应用、应用与授权、审批中心、运行管理、设置，共八项；
- `prototypes/ai-service-development.html:580-595` 实际把服务开发作为导航模块，并在同一原型内承载数据应用视图。

本报告的处理方式是：

1. 七项统计按用户指定口径，不把服务开发计为第八项；
2. 服务开发证据仍作为**跨功能支撑证据**用于 13.2、5.2.4(c)、14.4.1 和服务生产生命周期判断；
3. 服务开发原型不能用来证明七项中的工作台、服务集市、应用与授权或审批中心已经实现；
4. 正式规格必须消除此冲突。若最终导航保留八项，则七项功能评估不能代表完整数据服务域；若最终坚持七项，则需明确服务开发归入工作台、服务集市或其他一级功能的产品归属，否则会削弱 13.2 和 14.4 的责任闭环。

## 8. 优先级整改清单

### P0：先建立“可证明”的 14.4 核心闭环

1. **定义数据服务量化指标体系**：区分运行健康、管理过程、服务能力、应用效果、成本、价值和风险；为每个指标定义对象、分母、周期、来源、责任人、目标、阈值和保留期。
2. **建设真实遥测与证据链**：实现按租户、数据应用、服务产品、固定版本、环境、授权和数据权限关联的采集、持久化、查询和不可修改审计；把当前固定示例替换为生产数据。
3. **建立持续改进闭环**：指标异常或目标偏差必须能关联问题、责任人、措施、审批、实施、复测和复盘；能生成周期报告并保留历史版本。
4. **补齐服务方能力评价**：定义服务方/责任团队、评价维度、评分和评级、周期评估、异议复核、整改复评以及生态/产业链关系。
5. **明确 AI 定价是否进入产品范围**：若 DCMM 4 级是目标，需补数据产品成本与价值底座、价格建议模型、人工审批、解释、版本和效果回测；若不由本模块承担，应锁定责任系统和集成/取证接口。

### P1：补强质量、安全、审计与价值支撑

1. **服务质量门禁与数据质量联动**：接入相邻质量平台，展示来源资产质量规则、评分、时效、问题和阻断结果；服务版本固定质量证据引用。
2. **安全策略真实执行**：接入认证、密钥、网关、运行时、订阅适配器和数据安全域；用集成测试证明收紧阻断、到期/吊销、最小权限和高风险操作确认。
3. **审计高级能力**：实现审计数据采集、完整性校验、留存、导出/取证和跨链路关联；再评估 AI 异常与关联分析，不把普通筛选称为 AI 审计。
4. **资产/应用价值与成本**：建立成本台账、服务复用和应用效果指标，形成可追溯的价值/收益评估。
5. **AI 能力真实化**：将开发 Agent、AI 运维、合规/质量分析从原型升级为受控实现，保存模型版本、输入证据、输出、人工决策和效果指标。

### P2：形成组织级评估材料

1. 发布连续周期的数据服务、资产运营、质量、安全、运维和应用效果正式报告；
2. 建立内审与外审计划、发现、整改、复核和管理评审证据；
3. 形成角色职责、培训、制度、流程、指标评审和持续改进会议记录；
4. 保存国家/行业标准立项、参编、提案、会议和发布证明；
5. 建立评估证据目录，确保每项 DCMM 要求可追溯到制度、系统控制、运行记录、报告和改进结果，而不是只链接原型页面。
